# 管理后台：加载与性能

页面：`flipgame/Admin.html`。本页沿用中文管理界面、系统字体和现有独立 HTML 结构，不引入框架或远程字体。

## 已确认的问题与改动

以下对比以 `4440b56` 的后台实现为改动前基线。查询数量指业务查询，不包括每个受保护请求仍需完成的 session 和账号校验。

| 环节 | 改动前 | 当前实现 |
| --- | --- | --- |
| 后台首屏 | 先读 `/api/me`，再同时加载用户、价格、流量，共 4 个请求 | `/api/me` 后只加载当前页面，共 2 个请求；支持直接进入价格/流量的 hash |
| 用户列表邮箱 | 查询账号后逐个查询主邮箱，N 个用户约 N+1 次 SQL | 单次 LEFT JOIN 返回账号及有效主邮箱；服务端解密后仅返回掩码 |
| 流量记录 | 按天依次等待 Blob get，每一天内部无限制并发 | 所有日期的 Blob 由全局最多 8 个 worker 读取；SDK async iterable 完整处理分页 |
| 页面切换 | 首屏已经提前读取所有模块 | 未访问模块不读取，同一模块正在进行的请求合并；已有结果留在当前页面内存，刷新才重读 |
| 失败反馈 | 初始化任一请求失败，三个模块都显示失败 | 每个模块独立显示加载、成功和失败；刷新重试，不清空其他模块数据 |
| 价格编辑 | 保存中可重复点击、刷新可能覆盖输入 | 保存按钮只在数据载入且有修改时启用；保存/重载期间禁止重复操作，未保存重载需确认，切换模块保留输入 |

后台账号列表保留现有默认 200 / 最大 1000 条的服务端限制，搜索和角色筛选仍针对本次已加载列表；本次不增加分页产品功能。当前主邮箱由既有唯一索引约束为每账号至多一个有效主邮箱，联合查询不扩大邮箱输出范围。缺失或解密失败仍输出空掩码。

## 安全与缓存边界

- 每个 Admin API 仍独立执行 `requireRequestCapability(..., "isAdmin")`，不缓存或跳过服务端权限校验，也不改变 session 更新和 `authz_version` 检查。
- UI 结果仅保留在当前页面内存/DOM，不写 localStorage，不在账号之间共享。页面底部显示最近载入时间，刷新重新读取服务端。保存用户权限后重新加载用户列表。
- 当前管理员的角色编辑在 UI 中禁用；后端原有的自我降权/停用拒绝仍保留。
- 价格、停用和角色变更失败都给出可恢复提示，不自动重试写入；请求结果不明确时应刷新核对后再操作。
- `:8000` / `file://` 仍为明确的静态 Mock；真实 BFF 没有有效管理员 session 时不读取管理数据。
- 本次无数据库 schema 改动，无需新增 SQL 迁移。

## 验证和剩余不确定性

- 浏览器测试 `node --test flipgame/test/admin-workspace.test.mjs` 使用完全拦截的模拟 HTTPS API，无真实数据库写入；覆盖首屏请求数量、深链接、快速切换请求去重、局部错误、未认证阻断、价格编辑保留、角色写入错误与重复点击保护。
- 响应式截图覆盖 1440、768、390、320 CSS px 下的用户、价格和流量页面；数字、长账号名称、输入控件、空/失败状态均使用测试数据。
- 后端测试覆盖批量邮箱查询、缺邮箱/解密失败掩码、禁止逐用户查询、流量分页完整性与最大并发数。
- 这些结果验证了请求/查询结构和行为，不能等同于生产环境耗时。尚未量测真实管理员请求的 p50/p95、SQL RTT、Blob 数量、冷启动与跨区域网络开销，不给出未经测量的倍数或毫秒承诺。
- 如果发布后仍慢，下一步应按请求分别记录 session/账号解析、业务 SQL、Blob list/get 的阶段耗时，仅记录数量与时长，不记录邮箱、token、原始 Cookie 或生产数据。然后核对实际 Netlify Function 与数据库区域，以及 7/30/90 天记录数量；不要先扩大数据库连接池或取消权限检查。
